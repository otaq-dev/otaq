# Give tickets branches, not folders: a warm slot pool

Otaq should stop giving each ticket its own folder. Instead it should keep a **small, fixed pool of reusable working folders ("slots") that keep their build output**. A ticket owns only its **git branch**. It holds a slot while an agent works on it, and borrows one when someone clicks Run, opens a Shell, runs the validator or asks for rework. The deciding fact comes from measuring this repo. Moving a warm slot to a different ticket's branch takes **0.02–0.08 s for the `git switch` and 9–21 s for the rebuild**, because all **302 dependency units stay compiled** and only Otaq's own 4 crates recompile. So a Review ticket loses almost nothing by not having its own folder. Disk use is then capped by the number of slots, not the number of tickets, and that holds on macOS, Windows and Linux alike. No other option does that. Copy-on-write cloning, which seeds a new folder by sharing the original's disk blocks, is a real speed-up but only on some filesystems (always on Mac, rarely on Windows and Ubuntu). Shared-checkout tools like GitButler cannot keep 15 branches separately runnable. Containers can't build a Tauri desktop app at all. Slots also fix the "copied build folder breaks because it remembers its old path" problem for free: a slot's path never changes, so Python venvs, CMake folders and Cargo's records keep working whatever the project's stack. Below: how today's tools do it, why the cleverer-sounding alternatives fall short, what this repo's numbers say, and three designs, with the slot pool first.

## Every local tool still gives each task a full folder, and users hate the bill

Nearly every local agent tool (Claude Code, Cursor, Codex desktop, Conductor, Vibe Kanban, Superset) gives each task a plain git worktree, and leaves installing dependencies to a setup script the user has to write. Claude Code's docs say outright that "a worktree is a fresh checkout, so initialize your development environment there" ([Claude Code docs](https://code.claude.com/docs/en/worktrees)). Superset says each worktree "needs its own node_modules or virtualenv" ([Superset](https://superset.sh/compare/isolate-parallel-coding-agents)). The only thing they have converged on is `.worktreeinclude`, a list of ignored files such as `.env` to copy into new worktrees, now in Claude Code, Codex and Conductor ([Codex docs](https://learn.chatgpt.com/docs/environments/git-worktrees); [Conductor docs](https://conductor.build/docs/concepts/git-worktrees)). Nobody has solved zero-configuration setup locally.

The complaints follow from that. A Cursor user on Windows watched **two worktrees of a ~2 GB repo grow to 9.82 GB in 20 minutes**, with an estimated **140 GB in a week**, and called Cursor "unusable" ([Cursor forum](https://forum.cursor.com/t/windows-request-to-disable-automatic-worktree-creation-critical-disk-space-issue/146189)). Vibe Kanban's own docs warn that `node_modules`, `target/` and `build/` make multiple workspaces "consume significant disk space" ([Vibe Kanban](https://www.vibekanban.com/docs/workspaces/managing-workspaces)). Windows file locks held by Node processes block worktree removal ([claudeissues #41740](https://claudeissues.com/issue/41740-worktree-removal-fails-file-locks-prevent-cleanup-on-windows)). Rust users are stuck either way. A shared target folder makes "Cargo's directory lock make builds wait for each other", and separate ones recompile everything ([jdx.dev](https://jdx.dev/posts/2026-09-05-introducing-mr-boxington?a=1)).

The usual fix is to cap and delete. Cursor keeps 20 worktrees and sweeps every 6 hours ([Cursor forum](https://forum.cursor.com/t/windows-request-to-disable-automatic-worktree-creation-critical-disk-space-issue/146189)). Codex keeps the 15 most recent ([Codex docs](https://learn.chatgpt.com/docs/environments/git-worktrees)). That assumes worktrees are throwaway, which is exactly wrong for Otaq: 10–15 tickets sit in Review for days and each must stay runnable.

The cloud products solve install cost a different way. Codex cloud caches the container after setup for up to 12 hours and runs a "maintenance" script when it resumes ([OpenAI](https://learn.chatgpt.com/docs/environments/cloud-environment.md)). Jules snapshots after a successful setup ([Jules changelog](https://jules.google/docs/changelog/2025-08-05)). Devin boots every session from one organisation snapshot ([Devin docs](https://docs.devin.ai/onboard-devin/environment/blueprints.md)). The pattern is "pay for setup once, then reuse the warm result". The slot pool is the local, cross-platform version of that pattern. Practitioners have reached the same conclusion: recreating worktrees per task throws away "any build cache, compiled artifacts", so they keep persistent per-agent worktrees and rotate branches through them ([Upsun](https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents)). The jj tool `wsg` manages "a pool of workspaces as reusable worker slots" ([wsg](https://github.com/jarvvski/wsg)).

## Version-control tricks either share one folder or cost the same as worktrees

**GitButler** is the one real attempt to drop per-task folders. It applies several branches to one working folder at the same time and assigns each changed line to a branch. Claude Code hooks can open one branch per session automatically ([GitButler blog](https://blog.gitbutler.com/parallel-claude-code)). Trigger.dev moved its monorepo to it to escape repeated installs and duplicated services ([Trigger.dev](https://trigger.dev/blog/parallel-agents-gitbutler)). But the folder only ever holds all branches merged together. To run one branch alone you must remove the others from the folder (`but unapply`), which rewrites files under every agent still working ([GitButler docs](https://docs.gitbutler.com/commands/but-unapply)). A practitioner's write-up names the failure modes. "A branch label is not a file lock", so a second agent's stale full-file write silently erases the first agent's change. A green combined build doesn't prove that each branch builds on its own ([Wavect](https://wavect.io/blog/gitbutler-parallel-ai-agents-one-workspace/)). If two branches touch the same lines, the second is forced to stack on the first ([community skill](https://skillselion.com/skills/gitbutlerapp/gitbutler/but)), which collides with Otaq's decision to defer stacking. GitButler is also licensed under the Functional Source License, whose non-compete clause could reach a kanban that manages agent branches ([GitButler](https://blog.gitbutler.com/gitbutler-is-now-fair-source)). It fits "many agents typing at once". It does not fit "15 branches, each runnable alone, for days".

**Jujutsu (jj)** workspaces have the same structure as worktrees: one shared history plus a full working folder each. So they don't reduce build-output cost at all, and secondary workspaces have no `.git` folder, which confuses `gh`, IDEs and Claude Code's `--worktree` ([jj docs](http://docs.jj-vcs.dev/latest/working-copy/); [claudeissues #27466](https://claudeissues.com/issue/27466-worktree-flag-silently-fails-on-jj-jujutsu-colocated-repos-detached-head)). Two jj ideas are worth borrowing, and plain git can do both. First, jj treats the working copy as a commit that is saved automatically, so an agent's edits are never lost uncommitted. Second, "durable worker slots" get moved to new work instead of being deleted ([Medium](https://medium.com/@shrmtv/git-wasnt-designed-for-agents-7a5aaa11698f)).

A **plain shared checkout with locks or ownership rules** fails silently whenever two agents touch the same file, and one agent's syntax error breaks every other agent's build ([Medium](https://medium.com/@koriigami/running-parallel-claude-code-agents-on-a-single-codebase-927d70e7349d); [fast.io](https://fast.io/resources/claude-code-agent-teams-setup/)). Sub-agents sharing one checkout often "work fine" in practice. That matches the case where tasks touch different files and nobody needs to run one task's version alone. Otaq's Review column needs exactly that. Sparse checkout, partial clones and git alternates shrink source code and history. The source here is 31 MB and worktrees already share history, so they don't touch the real cost.

## Filesystem cloning is a Mac-first accelerator, not a cross-platform foundation

Copy-on-write ("CoW") cloning makes a copy that shares disk blocks with the original until one of them is written. It is the most effective trick in the research, and it splits sharply by operating system:

| OS | Where CoW works | Who has it by default | Admin needed |
|---|---|---|---|
| macOS | APFS, same volume only ([Eclectic Light](https://eclecticlight.co/2025/04/07/how-robust-are-apfs-clone-and-sparse-files/)) | Everyone | No |
| Linux | btrfs, XFS ([Enki](https://mintlify.wiki/korbindeman/enki/concepts/worker-isolation)) | Fedora (btrfs), RHEL family (XFS) ([Wikipedia](https://en.wikipedia.org/wiki/List_of_default_file_systems)) | No; ext4 (Ubuntu/Debian) silently does a full copy |
| Windows | Dev Drive (ReFS), Windows 11 24H2+ | Almost nobody; the C: drive can never be one | Yes, to create the drive ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/dev-drive/)) |

Tools already do this. git-cow clones ignored build caches into new worktrees with one call, but **deliberately skips `.venv` and CMake folders because they contain absolute paths** ([git-cow](https://github.com/onnimonni/git-cow)). mr-boxington is a shared Rust build cache that restores files by reflink, then hard link, then copy, on all three OSes ([jdx.dev](https://jdx.dev/posts/2026-09-05-introducing-mr-boxington?a=1)). There are warnings too. Apple "strongly discourages" cloning whole directories in one kernel call: it freezes changes to the source tree and can, at worst, panic the machine ([Apple Developer Forums](https://developer.apple.com/forums/thread/784446)). A t3code maintainer rejected default-on CoW seeding as a speed feature, not a disk saver ([t3code PR](https://github.com/pingdotgg/t3code/pull/12631)).

**Overlays** layer a private writable copy over a shared read-only base. On Linux they work without root from kernel 5.11 ([LKML](https://lkml.iu.edu/2012.2/01416.html)), but Ubuntu 24.04's AppArmor restricts the user namespaces they need ([Ubuntu](https://documentation.ubuntu.com/release-notes/24.04/)). macOS needs macFUSE, FUSE-T or FSKit, and Windows needs ProjFS, which must be turned on from an admin prompt. Each needs third-party pieces or user approval ([FUSE-T](https://github.com/macos-fuse-t/fuse-t); [Apple forum](https://developer.apple.com/forums/thread/838060); [ProjFS](https://www.nuget.org/packages/Microsoft.Windows.ProjFS)). **Snapshots** only work per directory on btrfs, where a normal user can create them ([btrfs-subvolume(8)](https://dokk.org/manpages/debian/12/btrfs-progs/btrfs-subvolume.8.en)). **Containers** give every task the same path and a private set of ports. But on Mac and Windows they run inside a Linux VM, which makes bind-mounted trees with many small files slow ([techearl](https://techearl.com/docker-bind-mounts-slow-mac-windows)). They need Docker or similar installed, Sculptor users call per-agent containers "very heavy for a dev laptop" ([Show HN](https://hn.svelte.dev/item/45427697)), and they can't build or run a macOS Tauri app. None of these meet "zero configuration on all three OSes".

The hidden trap under every copying approach is **paths baked into build output**. A Python venv moved to a new folder breaks. In one uv case a stale shebang silently ran the *system* pytest instead of the project's ([uv issue #10895](https://www.goodfirstissue.org/astral-sh/uv/issues/10895)). CMake build folders cannot be moved ([Kitware #20473](https://gitlab.kitware.com/cmake/cmake/-/issues/20473)). Cargo handles a moved target folder ([cargo docs](https://doc.rust-lang.org/stable/nightly-rustc/cargo/core/compiler/fingerprint/fn.target_root.html)), but changed paths and timestamps still trigger rebuilds ([cargo-mtime](https://rust-digger.code-maven.com/crates/cargo-mtime)). The research names the clean way out: give every task the *same* absolute path, so nothing baked in goes stale. Containers and Linux mount namespaces can fake that. **A slot that keeps one fixed path for its whole life gets the same benefit on every OS, with no tricks.**

## Shared caches help per ecosystem, but Otaq can't count on them

Some ecosystems already share well. pnpm's global virtual store turns each worktree's `node_modules` into symlinks only, so an extra agent "costs almost no extra disk space". pnpm documents this specifically for parallel AI agents, but it is still experimental and off by default ([pnpm](https://pnpm.io/git-worktrees); [pnpm global virtual store](https://pnpm.io/zh/next/global-virtual-store)). Bun hard-links or clones from a global cache by default ([Bun](https://bun.com/docs/pm/global-cache)). uv links venv files from its cache by default, as long as the cache is on the same volume ([uv commit](https://git.joshthomas.dev/mirrors/uv/commit/a3b61a264473183305b2f3489a602be1af6b5721); [pydevtools](https://pydevtools.com/handbook/how-to/how-to-manage-uv-cache-size/)).

Rust is the weak case, and it is the one behind the 36 GB. A shared target folder lets only one build run at a time ([cargo flock](https://doc.rust-lang.org/nightly/nightly-rustc/cargo/util/flock/fn.acquire.html)). sccache can't cache incremental builds or linked crates such as binaries and proc-macros ([sccache](https://github.com/mozilla/sccache/blob/main/docs/Rust.md)). Cargo's own cache shared across workspaces is a 2026 project goal aimed at nightly, and "stabilization will likely not be completed" this year ([Rust Project Goals](https://goals.rust-lang.org/2026/cargo-cross-workspace-cache.html)). npm, which this repo uses, shares only its download cache. Each of these is an accelerator for one ecosystem. None works across stacks, so none can be the foundation for an app that doesn't know the project's stack. Otaq can quietly use them when it detects them. It cannot build on them.

## This repo's numbers say the 36 GB is mostly not per-branch cost

The local measurements change the picture, so they get the most weight here. They were taken on 2026-10-16 on this 16-core APFS Mac while another agent was also running, so the times include some contention.

| What | Time | Disk actually used |
|---|---|---|
| `git worktree add` | 0.17 s | ~14 MB |
| CoW clone of the 36 GB, 108,500-file `target/` (`cp -Rc`) | 29.9 s | **~49 MB** |
| CoW clone of `node_modules` (11,805 files) | 3.1 s | ~3 MB |
| First `cargo build` in that clone | **25.7 s** (only the 4 Otaq crates; 302 dependencies "Fresh") | ~2.1 GB written |
| Slot hop, 32 commits away, then build | 0.08 s + **21.2 s** | +1.3 GB |
| Slot hop, 10 commits away, then build | 0.04 s + **20.0 s** | +2.0 GB |
| Slot hop, 1 commit away, then build | 0.02 s + **8.7 s** | +0.14 GB |
| Rebuild with nothing changed | 0.44 s | 0 |
| `cargo test --workspace --no-run` in the slot | 29.0 s | **+6.8 GB** |
| `cargo clippy` in the slot | 18.0 s | +0.8 GB |
| `npm ci` with a warm cache | 2.6 s | ~190 MB |
| Removing the scratch worktree afterwards | 18.0 s | freed **11.1 GB** |

Three conclusions follow. First, **of the 36 GB, 18 GB is Cargo's incremental-compilation cache**, built up over time. What one branch really adds is the rebuild of Otaq's own crates: about 2 GB per build and about 7–11 GB once tests are built. The 11.1 GB freed at the end is what one active slot accumulated in about five minutes. Second, cloning and slot reuse gave **nearly the same build time** (about 20–25 s for a far hop, 9 s for a near one), because in both cases git rewrites the changed files and every Otaq crate above them recompiles. Dependencies never recompiled, since `Cargo.lock` didn't change; the cost of a lockfile change was not measured. Third, CoW makes *creating* a folder cheap but not *keeping* one. **Fifteen CoW-seeded Review folders would each grow by 2–11 GB as they build and test, so 30–165 GB on a Mac**, and the full uncloned size on ext4 or NTFS. Slots grow too (+1–2 GB per hop), so they need a periodic sweep. But their total is roughly slot count × slot size, whatever the number of tickets.

## Three designs worth building, ranked

### 1. Warm slot pool: tickets own branches, slots own build output

**How it works.** Otaq keeps N slots, for example `~/.otaq/slots/<repo>/1..N`. Each is a git worktree that is never deleted, so its `target/`, `node_modules` and `.venv` stay warm at a fixed path. N defaults to the user's limit on parallel agents plus two spare slots for Review, and Otaq can size it once from free disk space. A ticket in Dev holds a slot. When the agent stops, Otaq commits everything on the ticket's branch (an automatic work-in-progress commit, the jj idea) and checks the folder is clean. The slot then goes back to the pool. Its build output stays, but the ticket's code is safe in git. When the user clicks Run or Shell on a Review ticket, or the validator or a rework agent starts, Otaq takes a free slot, preferring the one that last held that ticket, runs `git switch <branch>`, and hands over. If the slot still holds that ticket, Run is a 0.44 s no-op build. Otherwise it is a 9–21 s incremental build in this repo, with no reinstall, because the slot already holds a superset of the dependencies.

**Why it meets the goals.** It needs **zero stack knowledge and zero configuration**. Otaq never learns what `target/` or `.venv` is: the agent or the Run command builds as usual, and the slot simply remembers the result. It works the same on macOS, Windows and Linux, because it uses only `git worktree` and `git switch`. It **avoids path-baking by design**: a slot's path never changes, so venvs, CMake folders and Cargo's records stay valid. That is the "same path for every task" benefit without containers. Disk is **bounded by N**, not by the 10–15 tickets waiting in Review. With 6 slots of roughly 10–40 GB each in this repo, that is a planned budget rather than a 140 GB surprise.

**What it costs, honestly.** Opening a Review ticket that isn't already in a slot costs one incremental build (9–25 s here, longer if `Cargo.lock` changed). Two Review tickets can run side by side only if two slots are free. When all slots are busy with Dev agents, a Review Run must either wait or open a temporary overflow slot. Ignored files left by the previous branch, such as generated code in ignored folders or stale build files for deleted modules, can leak into the next ticket. Build tools usually handle this, but a "reset slot" action (delete ignored files, rebuild) is the escape hatch. Slots accumulate build output, so Otaq needs a stack-agnostic sweep, such as resetting any slot over a size budget while it is idle. Ports still collide between slots running at the same time. A slot's fixed number does give a natural, zero-config identity that Otaq can expose (for example `OTAQ_SLOT=3`) for agents to offset ports from, something no surveyed tool provides ([Superset](https://superset.sh/compare/isolate-parallel-coding-agents) only detects ports). One thing to check before building: Claude Code stores conversation history per working directory, so resuming a ticket's agent conversation in a *different* slot may not find the earlier session. Otaq must test this and, if needed, pin rework to the ticket's last slot or carry the context forward itself.

### 2. Slot pool with copy-on-write seeding and elastic overflow, where the filesystem allows

This is the same design plus one accelerator. When Otaq creates a slot, or a temporary overflow slot for a burst of Review runs, on APFS, btrfs/XFS or a Dev Drive, it clones the ignored folders from the warmest existing slot instead of building cold. Measured here: **~30 s and ~49 MB** to get a slot whose 302 dependencies are already built. It must clone file by file, not with a single directory clone, because of Apple's kernel warning. It should skip folders known to bake in paths, as git-cow does with `.venv` and CMake, or simply fall back to "delete ignored files and rebuild" if the first build fails. This makes the pool *elastic* on Macs: N can grow briefly when the user wants five Review tickets open at once, then shrink back. The seeded slots cost only what they rewrite. On Ubuntu's ext4 and ordinary Windows NTFS, Otaq detects that cloning isn't available and keeps the fixed pool, so it never silently makes full copies, which several projects refuse to do ([t3code PR](https://github.com/pingdotgg/t3code/pull/12631)). It is the best Mac experience without making other platforms worse.

### 3. Detect-and-share caches layered on the pool

Without asking the user, Otaq can check lockfiles and switch on the sharing that each ecosystem already supports. For pnpm, that means the global virtual store, which pnpm recommends for worktrees with AI agents ([pnpm](https://pnpm.io/git-worktrees)). Bun and uv already share by default; Otaq only needs to keep slots on the same volume as their caches. For Rust, a content-addressed cache such as mr-boxington would shrink cold slot creation on non-CoW machines ([jdx.dev](https://jdx.dev/posts/2026-09-05-introducing-mr-boxington?a=1)). This is a bonus layer, not a foundation, because it only helps stacks Otaq recognises. It still matters on Windows and Ubuntu, where design 2's cloning isn't available.

### Rejected, and why

GitButler-style shared folders can't keep Review branches separately runnable. Per-ticket CoW worktrees still grow with the number of tickets, and work only on some filesystems. Overlays and snapshots need drivers, admin rights or specific Linux setups. Containers can't build desktop apps and are heavy on laptops. jj costs the same as worktrees.

### Worth prototyping

There are four cheap experiments. (a) Pool size versus Run delay: measure how often Review Runs find their ticket still in its last slot at N = concurrency + 2. (b) The cost of a far hop when `Cargo.lock` changes, which wasn't measured. (c) Whether resuming a Claude Code session in a different slot loses the conversation. (d) A **"last build shelf"**: for projects whose Run produces a self-contained binary, keep that binary (about 60–70 MB here) next to the branch, so Run on a Review ticket can launch without borrowing a slot at all. Otaq can't know in general which output is the runnable one, so this is an optional fast path, not part of the core.

## Conclusion

The question was posed as "how do we make per-ticket folders cheap?", and the measurements show that is the wrong question. In this repo the expensive part, 302 compiled dependencies, is shared by every branch, and what differs between branches costs 9–21 s to rebuild. A folder per ticket therefore pays for isolation that a Review ticket only needs during the few minutes someone is running or reworking it. Once a ticket is a branch that *visits* a warm folder, disk scales with the number of agents working at once, not with how long the Review queue gets. The worst problem with copying build output, paths baked into it, also disappears, because the folders never move.

There is a real cost: opening a Review ticket that has fallen out of its slot means a short rebuild instead of an instant start. That is a trade the user can see and control (more slots means more instant starts), unlike a disk that quietly fills up. It also differs from the rejected "reuse Done worktrees" and "remove at Review" ideas in one important way. The pool is a fixed set of folders that Otaq manages, and no ticket ever owns, waits for or loses a folder. Copy-on-write, shared caches and the build shelf then become optional speed-ups on top of a design that already works on every OS without configuration.
