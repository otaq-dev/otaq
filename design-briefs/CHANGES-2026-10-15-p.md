# Design update P: a rich Markdown editor for "What and why" (2026-10-15)

The ticket description ("What and why") becomes a **rich Markdown editor** built on **Tiptap v3** with its official
Markdown extension. Only MIT packages are used: `@tiptap/core`, `@tiptap/react`, `@tiptap/starter-kit`, `@tiptap/markdown`,
`@tiptap/extension-list` and `@tiptap/extension-table`. **No Tiptap Pro extensions.** The main reason is copy and paste.
People paste from web pages, Google Docs, Slack and Claude, and copy descriptions back out, and the formatting must survive
both ways. The stored value stays plain Markdown: agents still read and write it with `otaq show` / `otaq update --stdin`.

Today the edit mode is a plain text area. Read mode shows only paragraphs, headings, code blocks and flat lists: task
boxes are dropped, and links, bold and tables aren't rendered. Briefs 08 (form and Ticket tab) and 05 (side panel) are
affected.

## Prompt to paste into the pen.dev design agent
```text
In Otaq, the ticket description field "What and why" changes from a plain text area to a rich Markdown editor (WYSIWYG).
It's built on Tiptap v3, which is headless: it brings no styling or toolbar, so you design all of it with Otaq's
existing tokens, type scale and components. The saved value is still plain Markdown text, because agents read and write
the same description from the command line. So design only what Markdown can express: no colors, font sizes, underline,
alignment, images or embeds.

Design it in crewboard.pen, frame groups "08 · Ticket editor" (the full form and the Ticket tab's edit mode) and
"05 · Ticket side panel" (the Ticket tab's read mode). Use Otaq Light and Otaq Dark, at 1440×900, and check it at
1280×800. Reuse the existing form layout, field label ("What and why"), hint and Save / Cancel row. Don't change any
other frame.

Supported content (this is the whole list):
   headings (H1–H3 in the menu; deeper levels from pasted text render like H3) · paragraphs · bold · italic ·
   strikethrough · inline code · links · bullet lists · numbered lists · task lists (- [ ] / - [x], checkable) ·
   nested lists · blockquotes · code blocks with an optional language label · horizontal rule · tables (simple,
   no merged cells).

1. Edit mode (the full form and the Ticket tab while editing):
   - A compact toolbar on top of the field: Heading (dropdown H1–H3 / Text), Bold, Italic, Strikethrough, Inline code,
     Link, Bullet list, Numbered list, Task list, Quote, Code block, Table, Horizontal rule. Use Lucide icons with
     tooltips that show the shortcut (⌘B, ⌘I, ⌘⇧X, ⌘E, ⌘K, ⌘⇧8, ⌘⇧7, ⌘⇧9, ⌘⇧B …). On narrow widths the least-used
     buttons move into a "…" overflow menu.
   - Markdown shortcuts while typing also work: "## " becomes a heading, "- [ ] " a task, "```" a code block,
     **text** bold. Annotate this; it doesn't need its own toolbar UI.
   - A small "Markdown" toggle at the right end of the toolbar switches to the raw Markdown source (monospace, same
     field size) and back. It's for people who prefer typing Markdown and for checking what agents will read.
   - The field grows with its content up to a max height, then scrolls inside, and the toolbar stays pinned.
   - The placeholder stays "Context, constraints, links…". The hint "Markdown · code blocks" becomes
     "Markdown · paste keeps formatting".
2. Link editing: ⌘K or the Link button opens a small popover with a URL field, Apply and Remove. Hovering or putting
   the caret on an existing link shows a mini bubble: the URL (truncated), Open, Edit, Remove.
3. Code blocks: a monospace block in the existing code-block style, with a language label at the top right that can be
   picked from a short list (none, bash, rust, ts, json, diff …). Tab indents inside the block.
4. Tables: when the caret is in a table, a small contextual bar shows add row above/below, add column left/right,
   delete row, delete column and delete table. The header row is styled like the app's other tables.
5. Read mode (the Ticket tab in the side panel): the same rendering without the toolbar. Task checkboxes look real but
   are read-only in read mode (annotate this). Links open in the system browser. Code blocks get a "Copy" button on
   hover. Add a "Copy as Markdown" icon button next to the existing Edit button. It copies the whole description as
   Markdown text, so it pastes cleanly into Claude, GitHub or Slack, and it shows a "Copied" state.
6. Copy and paste behaviour (annotate it on the frames; one small frame can show before and after):
   - Pasting from a web page or Google Docs keeps headings, lists, bold, links, code and tables. It drops colors,
     fonts and images, and nothing appears that Markdown can't save.
   - Pasting plain Markdown text (e.g. from Claude) is turned into formatting.
   - ⌘⇧V pastes as plain text.
   - Copying a selection puts both rich text and Markdown on the clipboard.
7. "Updated by agent" (brief 08 §4) stays. Its before/after compare now shows the rendered description, with a toggle
   to compare the Markdown source.

States to draw:
   a. Empty field with the placeholder and toolbar (light and dark).
   b. Filled description, edit mode, using the example below (light and dark).
   c. The same description in read mode in the side panel, with "Copy as Markdown" and its "Copied" state.
   d. The Markdown source toggle on, showing the same content as raw text.
   e. The link popover, and the hover bubble on an existing link.
   f. The caret in a table, with the table contextual bar.
   g. A code block with the language picker open.
   h. The toolbar overflow at the Ticket tab's narrow width (side panel at 1280×800).
   i. The field at max height, scrolled, with the toolbar pinned.
   j. Editing while the ticket's agent works: the existing note under Save ("SHOP-19's agent will be told what
      changed.") stays as it is.

   - [ ] Works with the existing `AddressForm` validation
   | Field | Source |

   | Postcode | Places API, editable |
   ```ts

Annotate the keyboard shortcuts, that the stored value is Markdown, that the toolbar and the source toggle are

List anything unclear or contradictory under "Open questions" instead of designing it silently.
